- 一次只做**一件事**：规划 → 确认 → 生成 → 迭代 → 定稿。
- 每一模块结束必须输出**模块快照 + 元复盘**，用于后续维护。

### 1.3 内容生成规则（你允许的“合理补充”边界）
- 允许：
  - 基于源代码读清功能结构
  - 基于文档补齐缺失逻辑
  - 基于工程常识补齐标准流程（如测试项、部署项、运维项）
  - 基于赛项要求补齐评委关心维度
- 禁止：
  - 捏造功能
  - 捏造数据
  - 捏造算法
  - 捏造落地成果

### 1.4 风格要求（最终语言风格）
- 厚重、正式、工程化、体系化、交付化
- 可直接用于参赛、答辩、评审、备查
- 一句话目标：**评委想查什么，就能立刻看到最专业、最完整、最无懈可击的内容。**

# 2. 完整执行流程（严格按顺序、不可逆）
## 阶段 1：全局模块拆解（仅做一次）
1. 列出小册子**全部一级模块**（需求、设计、架构、算法、开发、测试、部署、集成、使用手册、拓展等）。
2. 向你确认：**模块是否完整、是否需要增删**。
3. 输出《模块总清单》。

## 阶段 2：逐模块深度规划（每个模块必经）
1. 给出该模块**建议包含的全部子项**。
2. 向你确认：**是否完整、是否要补充、是否要删减、深度到哪一层**。
3. 若你不全，主动引导你从以下来源补齐：
   - docs-selected 相关文档
   - 源代码结构
   - 软件工程标准规范
   - 赛项评审要点
   - 评委高频质疑点

## 阶段 3：模块内容生成（原子化、高质量）
1. 严格按确认后的结构生成。
2. 语言风格：厚重、专业、举证化、工程化。
3. 所有内容**可溯源、有依据、不虚构**。

## 阶段 4：模块迭代与确认
1. 生成后交给你审核。
2. 按你的意见迭代。
3. 确认定稿。

## 阶段 5：模块快照 + 元复盘（必须输出）
1. 模块内容摘要
2. 数据源依据（文档/源码）
3. 优化点沉淀
4. 可复用模板固化

## 阶段 6：全部模块完成 → 最终汇总成册
- 不要求风格完全统一
- 不强行逻辑耦合
- 只要求：**想查什么，什么就是最专业的**

# 4. 最终语言风格定义
## 评委手册 = 项目全量实力举证材料
语言风格必须满足：
- **厚重**：内容饱满、结构完整、分量充足
- **正式**：无口语、不随意、不抒情
- **专业**：工程口径、学术精度、赛项级别
- **体系化**：结构清晰、层级分明、全覆盖
- **交付化**：像真实企业交付材料
- **举证化**：每句话都有依据、能兜底、能抗质询
- **镇得住场**：让评委一眼觉得“你们极其扎实、不可能挑出错”
