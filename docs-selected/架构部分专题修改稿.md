## 一、架构部分要传达什么信息？

当前页面9和页面10的核心问题：**只列了有什么，没说为什么这样设计**。

评委看架构图，关心的是三个问题：
1. **你面对什么约束？**（为什么不能直调大模型？为什么需要编排层？为什么需要降级？）
2. **你做了什么选择？**（薄业务重编排、能力下沉、模型解耦、知识优先）
3. **这些选择解决了什么问题？**（系统韧性、可扩展性、教学一致性）

所以架构部分需要传达的**不是组件清单**，而是**设计决策及其理由**。

### 重构后的页面9 内容

**页面标题**：薄业务重编排：四层架构与关键设计决策

**架构图四层内容重构**（每层补充设计理由）：

```
前端交互层 · Vue 3 + TypeScript
├── 教师端：课件管理 · 脚本编辑 · 学情分析
├── 学生端：课程学习 · 上下文问答 · 断点续学
└── 泛雅集成入口：OpenAPI 轻量接入

业务编排层 · Go 后端（设计理由：不承担AI推理，只做状态编排与流式转发）
├── 学习状态机：讲授 → 遇疑 → 问答 → 三态续接 → 回到讲授
├── SSE 流式协议：逐词推送 + 完整回答 + 结构化元数据（理解程度 + 续接位置）
├── 课件上传管道：DB事务 → 文件存储 → AI解析（主引擎 + 降级引擎） → 节点生成
└── OpenAPI 适配：多键名兼容 + 字段级加密 + 异步任务对接

AI 能力层 · Dify 工作流 + Python 解析引擎（设计理由：能力下沉一次，教学场景持续复用）
├── 课件解析工作流：拆页 → 结构化 → 校验 → 入库
├── 知识入库工作流：切片 → 向量化 → 索引构建
├── 智能问答工作流：意图识别 → 课程知识优先检索 → 上下文增强 → 生成回答
├── 脚本生成工作流：节点内容 → 结构化脚本 → 逐节点音频
└── 语音生成工作流：文本 → 语音合成 → 音频与时长输出

基础设施层 · 数据与存储
├── PostgreSQL：结构化数据（课程、节点、用户、学习记录、会话）
├── Redis：会话状态 · 解析任务队列 · 进度游标 · 语义缓存
└── MinIO：课件原文件 · 页预览图 · 音频文件 · 解析结果
```

**图旁/图下标注三个关键设计决策**：

```
决策一：薄业务重编排
Go 后端只做状态编排和流式转发，不做AI推理。
→ 理由：AI推理延迟不可控（3-5秒），编排层必须轻量才能保证响应。

决策二：双引擎自动降级
Dify 主引擎不可用时，自动切换到本地 Python 引擎。
→ 理由：教学场景对可用性要求高，单引擎故障不能中断课堂。

决策三：SSE 三事件流式协议
不是简单文字流，而是逐词推送 + 完整回答 + 结构化元数据。
→ 理由：学生端需要理解程度和续接位置，这些是结构化数据，不能混在回答文本里。
```

## 三、页面10 重构方案

### 原页面10 的问题

| 问题 | 具体表现 |
|------|----------|
| 四个优势点是原则声明，没有具体实现 | "能力下沉""模型解耦""流程编排""知识优先"都是抽象概念，评委无法判断你是否真的做到了 |
| Workflow 编排层只画了线性流程 | "解析→入库→生成→保存→推送"没有条件分支、没有异常处理 |
| RAG 知识库只是一个框 | 没说清知识怎么入库、怎么检索、怎么约束幻觉 |
| 上下关系是线性堆叠 | 没有体现"能力如何下沉"和"模型如何解耦" |

### 重构方向

页面10 从"四个原则声明"重构为"**四个设计原则 + 每个原则的实现机制**"。

核心转变：不再只是说"我们做到了X"，而是说"我们面对Y问题，选择X方案，实现方式是Z"。

### 重构后的页面10 内容

**页面标题**：架构优势：四个设计原则及其实现机制

**原则一：能力下沉，教学场景持续复用**

问题：如果每个功能都直接调大模型，功能越多，重复调用越多，维护越困难。
方案：将课件解析、知识检索、内容生成、智能问答等能力统一封装为服务，通过工作流编排按场景组合调用。
实现机制：
- 5 个 Dify 工作流（课件解析、知识入库、智能问答、脚本生成、语音生成）覆盖全部 AI 场景
- 每个工作流内部按阶段编排，而非一次性调用
- 课件解析产出的知识对象是后续所有工作流的共享输入——解析一次，问答、生成、续接都消费同一套节点化内容

**原则二：业务与模型解耦**

问题：如果业务逻辑直接依赖某个大模型的 API，换模型就要改业务代码。
方案：通过模型适配层屏蔽底层差异，业务层只关心"我要做问答""我要生成脚本"，不关心底层是哪个模型。
实现机制：
- 业务编排层通过统一接口调用 AI 能力层，不直接调用模型 API
- 模型切换只需在适配层修改，业务代码零改动
- 当前已接入通义千问，通过适配层可平滑切换到其他模型

**原则三：工作流编排驱动**

问题：课件解析不是一次模型调用，而是一条多阶段流程（拆页→识别→聚合→重构→校验→入库），每阶段有不同输入输出和容错需求。
方案：用 Dify 工作流编排多阶段流程，而非在业务代码中硬编码调用链。
实现机制：
- 课件解析工作流：拆页→结构化→校验→入库，每阶段独立可观测
- 智能问答工作流：意图识别→课程知识优先检索→上下文增强→生成回答
- 工作流内部可做条件路由和异常回退，业务代码不需要处理

**原则四：课程知识优先，降低幻觉**

问题：通用大模型直接回答学生问题，容易产生偏离课件内容的幻觉答案。
方案：问答时优先检索当前课程的知识内容，再用大模型基于检索结果生成回答，而非让模型"自由发挥"。
实现机制：
- 课件解析后自动将内容切片索引化，构建课程专属知识库
- 问答时采用三级级联检索：当前页内容优先→邻近页补充→全局知识兜底
- 回答绑定溯源页码，学生可验证答案来源，降低幻觉

**页面底部总结句**：

> 四个原则不是空话——每个原则都有对应的实现机制：能力下沉靠工作流复用，模型解耦靠适配层，流程编排靠 Dify 工作流，知识优先靠三级级联检索。系统不是在某个点上做得好，而是在架构层面保证了教学一致性、系统韧性和可扩展性。

## 四、两页之间的逻辑衔接

### 页面9 → 页面10 的过渡逻辑

页面9 说的是"系统怎么组织"（四层架构 + 三个设计决策）。
页面10 说的是"为什么这样组织"（四个原则 + 实现机制）。

两页之间的关系是**结构→理由**：

- 页面9 的"薄业务重编排"对应页面10 的"工作流编排驱动"
- 页面9 的"双引擎降级"对应页面10 的"业务与模型解耦"（降级是解耦的韧性体现）
- 页面9 的"SSE三事件协议"对应页面10 的"能力下沉"（结构化元数据是能力下沉的具体产物）
- 页面10 的"课程知识优先"在页面9 的 AI 能力层中有直接体现（知识入库工作流）

### 答辩口述衔接建议

> 从页面9翻到页面10时可以说："架构图展示了系统的四层组织方式和三个关键设计决策。接下来这页回答一个更根本的问题——为什么要这样设计？我们提炼了四个设计原则，每个原则都不是空话，而是有具体的实现机制支撑。"
