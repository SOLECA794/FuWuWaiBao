## 子项详细规划

### 03-01：四层架构详细拆解

**目标：** 每层不是组件列表，而是回答三个问题——这一层为什么存在？它承担什么职责？它和上下层怎么通信？

| 层次 | 技术栈 | 设计目的 | 职责边界 | 层间通信协议 | 关键机制 | 源码回溯 |
|------|--------|---------|---------|-------------|---------|---------|
| 前端交互层 | Vue 3 + TypeScript | 分离UI渲染与业务逻辑 | 教师端课件管理/脚本编辑/学情查看；学生端课程学习/问答/续学；泛雅OpenAPI轻量嵌入 | HTTPS API调用编排层；WebSocket/SSE接收流式数据 | 组件化双向绑定、路由懒加载、流式内容渲染 | frontend/ |
| 业务编排层 | Go (Gin/WebSocket) | 做状态编排与流式转发，不承担AI推理 | SSE流式协议、学习状态机、课件上传管道、OpenAPI适配、鉴权与会话管理 | RESTful API对外暴露；内部gRPC/HTTP调用AI能力层 | SSE三事件协议（token/sentence/final）、任务状态机（pending→running→success/failed）、双引擎降级路由 | backend/internal/handler/student.go, teacher.go, service/ |
| AI能力层 | Dify Workflow + Python引擎 | 将AI能力下沉为可复用工作流，而非单点调用 | 课件解析/知识入库/智能问答/脚本生成/语音合成五大工作流 | 工作流内部阶段编排；对外通过OpenAPI或内部HTTP | 三阶段解耦管线（build_stage1→stage2→stage3）、VLM渐进增强、JSON Schema强制结构化输出 | ai_engine/generator.py, parser.py, schema.py, qa.py |
| 数据支撑层 | PostgreSQL/Redis/MinIO | 结构化持久化 + 缓存加速 + 文件对象存储 | PostgreSQL: 课程/节点/用户/学习记录/会话；Redis: 会话状态/队列/游标/语义缓存；MinIO: 课件原文件/预览图/音频 | 编排层通过驱动访问；AI能力层通过中间件访问 | 字段级AES-256-GCM加密、SHA-256内容哈希缓存失效、连接池管理 | backend/internal/model/models.go, service/ |

**产出格式：** 每个子层独立小节 → 设计目的 → 职责边界 → 关键机制 → 源码路径索引 → 数据流转图（文字描述+mermaid示意）

### 03-02：关键设计决策全解

**目标：** 每个决策回答"为什么选这个不选那个"——设计缘由、落地实现、故障降级逻辑。区别于PPT的概要陈述，手册需要展开到工程细节层面。

| 决策 | 设计缘由 | 落地实现 | 故障降级逻辑 | 源码回溯 |
|------|---------|---------|-------------|---------|
| **D1: 编排与能力分离** | AI推理延迟不可控(3-5s)，若编排层也做推理，则整体响应被拖慢；两层分离后编排层可以保持ms级响应，独立水平扩展 | Go编排层只做状态机管理、SSE转发、请求路由；所有AI调用下沉到Dify工作流/Python引擎；编排层通过接口调用而非代码内嵌 | 编排层不依赖AI能力层的实时响应——流式转发天然容忍延迟波动；编排层自身无状态，可多实例部署 | backend/internal/handler/teacher.go, student.go |
| **D2: 能力可降级** | Dify作为工作流引擎是单点依赖，一旦宕机整个AI能力层不可用；教学场景对可用性要求高 | 主引擎(Dify)→本地引擎(Python:8000)双注册；客户端先尝试Dify，返回错误码自动切到本地；本地引擎实现完整功能子集 | Dify不可用→自动切换本地引擎（fallbackURL=localhost:8000）；切换过程由编排层透明处理，对用户无感；恢复后自动切回主引擎 | backend/internal/service/dify_client.go (fallbackURL L196) |
| **D3: 节点化统一语言** | 传统方案以"页"为单位——但页的粒度太粗：编辑脚本无法精确到页内段落、问答溯源无法定位页内位置、续接无法精确恢复 | 页→节点拆分（TeachingNode结构）；双重映射（KnowledgeNodesJSON知识图谱+ScriptSegmentsJSON脚本片段）；节点引用一致性修复 | 节点引用破损→align_node_segment_mapping双向对齐修复；孤立节点引用→ScanOrphanTeachingNodeReferences跨11表扫描 | backend/internal/model/models.go (TeachingNode), ai_engine/schema.py (align), service/knowledge_graph.go (ScanOrphan) |
| **D4: 课程知识优先** | 通用大模型直接回答学生问题易产生脱离教材的幻觉答案；教学场景要求每个回答都可溯源 | 三级级联上下文（目标节点脚本→当前页内容→全页拼接）→优先检索课程内容→大模型基于检索结果生成→回答绑定溯源页码 | LLM不可用时降级到关键词匹配（中文教育关键词集RETEACH_KEYWORDS）；理解度判定双路策略 | backend/internal/handler/student.go (buildNodeScopedContext), ai_engine/qa.py (UNDERSTANDING_*, RETEACH_KEYWORDS) |

**产出格式：** 每个决策独立一节 → 问题陈述 → 决策内容 → 设计理由 → 落地实现 → 降级/容错 → 对比（如果选另一种方案会怎样）

### 03-03：中间件部署设计

**目标：** 不是"我们用了什么中间件"，而是"我们为什么用这个中间件、怎么部署的、出了什么问题怎么办"

| 中间件 | 选型理由 | 部署方式 | 核心职责 | 关键设计 | 故障预案 |
|--------|---------|---------|---------|---------|---------|
| PostgreSQL | 结构化数据强一致性要求、事务支持、JSONB适配半结构化字段 | Docker容器化部署 | 课程/节点/用户/学习记录/会话/知识图谱持久化 | 索引优化策略、事务隔离级别、连接池配置 | 主从备份、定期dump |
| Redis | 高吞吐低延迟缓存、支持队列/发布订阅多种数据结构 | Docker容器化部署 | SSE会话状态、解析任务队列、进度游标、语义缓存 | 缓存失效策略、连接池、键空间设计 | 哨兵模式高可用、RDB/AOF持久化 |
| MinIO | S3兼容对象存储、轻量私有化部署 | Docker容器化部署 | 课件源文件、页预览图片、音频文件、解析结果JSON | SHA-256内容哈希缓存、分段上传 | 多节点部署、Erasure Coding |

**产出格式：** 每个中间件独立小节 → 选型论证 → 部署架构 → 关键设计 → 故障预案

### 03-04：对外集成架构

**目标：** 展示"你们的系统不是孤岛，可以跟外部平台对接"

| 集成方面 | 内容 |
|---------|------|
| 集成方式 | RESTful OpenAPI（与泛雅平台对接） |
| 鉴权机制 | Token鉴权 + 字段级AES-256-GCM加密（crypto.go） |
| 接口规范 | 统一返回结构、错误码规范 |
| 数据交换格式 | JSON（多键名兼容设计——适配泛雅原有键名） |
| 异常处理 | 超时重试、错误码分级、异步任务回调 |
| 源码追溯 | backend/internal/handler/ + service/dify_client.go |

**产出格式：** 集成架构概述 → OpenAPI接口清单 → 鉴权与安全设计 → 异常处理策略
