# 泛雅权限体系与数据体系对接说明

更新时间：2026-05-25

本文档说明当前系统与泛雅平台对接时，权限如何判定、数据如何落表、同步接口如何使用，以及联调时应该遵循的字段约定。

---

## 1. 对接目标

当前实现不是把“权限”做成一张独立的大表，而是采用“角色字段 + 选课关系 + 课程归属”驱动的轻量权限体系：

- 平台侧用户先同步为统一用户实体。
- 课程、班级、选课关系分别落到独立数据模型。
- 学生是否可见某门课，主要由选课关系决定。
- 教师是否可管理某门课，主要由课程归属和教师选课关系决定。

这样做的好处是：

- 泛雅侧数据可以直接按组织、课程、班级、用户分层同步。
- 业务侧可以只依赖少量关键字段完成权限判断。
- 后续若要扩展更细粒度权限，也可以在现有模型上增补，而不需要推翻同步链路。

## 2. 当前权限体系

### 2.1 系统内身份模型

系统内有两类“身份”概念，需要区分：

1. 登录身份
   - 对应系统用户表 `User`。
   - 用于内部登录认证、JWT 颁发和前端会话。
   - 角色只有 `teacher` / `student`。

2. 平台同步身份
   - 对应平台用户表 `PlatformUser`。
   - 用于承载泛雅/学习通一侧同步进来的组织、课程、班级和选课信息。
   - 也是平台数据权限判断的基础。

### 2.2 角色含义

当前系统中的角色主要有三层：

| 角色字段 | 取值 | 含义 |
|---|---|---|
| `User.Role` | `teacher` / `student` | 内部登录身份 |
| `PlatformUser.Role` | `teacher` / `student` | 平台同步身份 |
| `CourseEnrollment.Role` | `teacher` / `student` | 某个课程/班级下的关系角色 |

使用规则：

- `teacher` 表示课程管理者、授课者或班级维护者。
- `student` 表示课程学习者。
- 如果同步请求未显式给出角色，默认按 `student` 处理。

### 2.3 权限判断原则

当前实现没有单独的 ACL / RBAC 权限表，权限主要通过下面几条数据规则组合判断：

- 用户是否是教师：看 `PlatformUser.Role` 或登录用户 `User.Role`。
- 用户是否属于某个教学班：看 `CourseEnrollment`。
- 用户是否能看到某门课程：看该课程下是否存在有效的选课关系，或是否是课程负责人。
- 用户是否能管理某门课程：看 `TeachingCourse.TeacherID`、课程下的教师选课关系，以及平台侧同步来的教师身份。

### 2.4 状态字段的含义

系统中与权限最相关的状态字段是：

| 字段 | 含义 | 建议值 |
|---|---|---|
| `status` | 数据是否可用 | `active` 为可用 |
| `role` | 身份角色 | `teacher` / `student` |
| `orgCode` | 组织归属 | 学校或机构编码 |
| `schoolName` | 组织名称 | 学校名称 |
| `classExternalID` | 平台班级外部标识 | 用于幂等同步 |

## 3. 数据体系

### 3.1 核心实体

当前平台数据主链路由四类实体组成：

| 实体 | 作用 | 主键/外部键 | 说明 |
|---|---|---|---|
| `PlatformUser` | 平台统一用户 | `ID` / `ExternalID` | 承载平台侧用户、教师、学生 |
| `TeachingCourse` | 教学课程 | `ID` / `ExternalID` | 课程运营主实体 |
| `CourseClass` | 教学班 | `ID` / `ExternalID` | 课程下的班级/行政班映射 |
| `CourseEnrollment` | 选课关系 | `ID` / 组合范围 | 用户、课程、班级之间的关联 |

### 3.2 实体字段说明

#### 3.2.1 PlatformUser

关键字段：

| 字段 | 说明 |
|---|---|
| `PlatformID` | 平台来源标识 |
| `ExternalID` | 平台侧用户唯一标识 |
| `Username` | 用户名，默认与外部 ID 一致 |
| `DisplayName` | 展示名 |
| `Role` | `teacher` / `student` |
| `OrgCode` | 学校或组织编码 |
| `SchoolName` | 学校或组织名称 |
| `Major` | 专业 |
| `Grade` | 年级 |
| `ClassExternalID` | 班级外部 ID |
| `ClassName` | 班级名称 |
| `Email` / `Phone` | 联系方式，当前存储为加密后文本 |

#### 3.2.2 TeachingCourse

关键字段：

| 字段 | 说明 |
|---|---|
| `PlatformID` | 平台来源标识 |
| `ExternalID` | 课程外部 ID |
| `Code` | 课程编码 |
| `Title` | 课程名称 |
| `TeacherID` | 课程负责人内部 ID |
| `OrgCode` | 组织编码 |
| `SchoolName` | 学校名称 |
| `Semester` | 学期 |
| `Status` | 课程状态 |
| `Credit` | 学分 |
| `Period` | 学时 |
| `CoverURL` | 课程封面 |

#### 3.2.3 CourseClass

关键字段：

| 字段 | 说明 |
|---|---|
| `PlatformID` | 平台来源标识 |
| `ExternalID` | 班级外部 ID |
| `TeachingCourseID` | 所属课程 |
| `TeacherID` | 班级负责人或授课教师 |
| `ClassName` | 班级名称 |
| `ClassCode` | 班级编码 |
| `Semester` | 学期 |
| `Grade` | 年级 |
| `Major` | 专业 |
| `Capacity` | 容量 |
| `Status` | 班级状态 |

#### 3.2.4 CourseEnrollment

关键字段：

| 字段 | 说明 |
|---|---|
| `PlatformID` | 平台来源标识 |
| `ExternalID` | 选课外部 ID |
| `TeachingCourseID` | 所属课程 |
| `CourseClassID` | 所属班级 |
| `UserID` | 关联用户 |
| `Role` | 选课角色 |
| `Status` | 选课状态 |
| `EnrolledAt` | 入选时间 |

### 3.3 关系主线

当前数据关系可以理解为：

```text
PlatformUser  ->  CourseEnrollment  ->  CourseClass  ->  TeachingCourse
```

实际使用中：

- `PlatformUser` 代表“这个人是谁”。
- `CourseEnrollment` 代表“这个人属于哪门课/哪个班”。
- `CourseClass` 代表“这个班属于哪门课”。
- `TeachingCourse` 代表“这门课本身是什么”。

## 4. 同步规则

### 4.1 用户同步 `syncUser`

接口：`POST /api/v1/platform/syncUser`

行为：

- `userInfo.userId` 是硬必填。
- `platformId` 推荐在顶层传入，便于统一归属。
- `userInfo.role` 不传时默认 `student`。
- `contactInfo.email`、`contactInfo.phone` 会写入加密后的联系方式字段。
- 若请求中包含 `relatedCourseIds` / `courseIds` / `teachingCourseIds`，会进一步创建或更新选课关系。

推荐请求结构：

```json
{
  "platformId": "plat_test",
  "userId": "plat_stu_test",
  "userInfo": {
    "userId": "plat_stu_test",
    "userName": "李四",
    "contactInfo": {
      "email": "lisi@example.com",
      "phone": "13800138000"
    }
  }
}
```

返回结果中通常包含：

- `internalUserId`
- `authToken`
- `syncStatus`
- `enrollmentCount`
- `linkedCourses`
- `userProfile`

### 4.2 课程同步 `syncCourse`

接口：`POST /api/v1/platform/syncCourse`

行为：

- 课程外部 ID 为空时会直接报错。
- 如果课程里带教师信息，会先同步教师用户，再把教师作为课程负责人写入 `TeachingCourse.TeacherID`。
- 若未提供班级列表，会自动生成一个默认班级。
- 同步完成后，会为教师创建对应的教师选课关系。

推荐请求结构里至少包含：

- `courseInfo.courseId`
- `courseInfo.courseName`
- `courseInfo.teacherInfo`
- 可选的 `schoolId`、`schoolName`、`semester`、`credit`、`period`、`courseCover`

### 4.3 幂等规则

当前实现中，幂等主键主要依赖：

- `PlatformUser.ExternalID`
- `TeachingCourse.ExternalID`
- `CourseClass.ExternalID`
- `CourseEnrollment` 的用户、课程、班级组合范围

建议对接方保持以下原则：

- 用户外部 ID 必须稳定且唯一。
- 课程外部 ID 必须稳定且唯一。
- 班级外部 ID 必须稳定且唯一。
- 同一用户同一课程同一班级的选课关系，应保持同一个外部 ID 或可重复写入的稳定组合。

## 5. 权限与数据的对应关系

### 5.1 学生权限

学生能看到什么，主要取决于：

- `PlatformUser.Role = student`
- 存在有效的 `CourseEnrollment` 记录
- 该选课记录关联到有效的课程和班级

学生端常见能力包括：

- 查看课件列表
- 进入学习会话
- 获取脚本
- 上报进度
- 进行问答
- 查看断点、笔记、收藏、薄弱点

### 5.2 教师权限

教师能管理什么，主要取决于：

- `PlatformUser.Role = teacher`
- 课程的 `TeacherID` 归属
- 课程下存在教师选课关系

教师端常见能力包括：

- 上传和管理课件
- 生成和编辑讲稿
- 查看学情、卡点、提问记录
- 管理课程班级和成员

### 5.3 组织权限

组织维度主要通过 `OrgCode` 和 `SchoolName` 表示：

- 同一组织下的数据可以聚合查询。
- 平台总览、用户列表、课程列表、班级列表都支持按组织过滤。
- 对接方如果有多校区/多租户场景，必须保证 `OrgCode` 稳定。

## 6. 接口层约定

### 6.1 无签名内部接口

`/api/v1/platform/*` 是当前系统内部统一 REST 接口，主要用于管理和调试，不要求 `enc` 签名。

### 6.2 泛雅开放适配层

`/api/v1/open/platform/*` 是泛雅风格开放接口，启用 `OPEN_API_STATIC_KEY` 后需要携带：

- `enc`
- `time`

当前实现默认签名字段为：

- `platformId`
- `userId`

如果需要扩展签名字段，可通过环境变量 `OPEN_API_SIGN_FIELDS` 配置。

### 6.3 当前建议

- 泛雅对接请求优先走开放适配层。
- 内部页面和运维接口优先走 `/api/v1/platform/*`。
- 同步请求里，顶层保留 `platformId` 与 `userId`，业务体放在 `userInfo` / `courseInfo` 内部。

## 7. 数据对接建议

### 7.1 建议的字段映射

#### 用户

| 泛雅字段 | 本系统字段 | 说明 |
|---|---|---|
| `userId` | `PlatformUser.ExternalID` | 必须稳定唯一 |
| `userName` | `PlatformUser.DisplayName` | 展示名 |
| `role` | `PlatformUser.Role` | 默认 `student` |
| `orgCode` / `schoolId` | `PlatformUser.OrgCode` | 组织编码 |
| `schoolName` | `PlatformUser.SchoolName` | 学校名称 |
| `major` | `PlatformUser.Major` | 专业 |
| `grade` | `PlatformUser.Grade` | 年级 |
| `classId` / `classCode` | `PlatformUser.ClassExternalID` | 班级外部 ID |
| `className` | `PlatformUser.ClassName` | 班级名称 |
| `contactInfo.email` | `PlatformUser.Email` | 加密存储 |
| `contactInfo.phone` | `PlatformUser.Phone` | 加密存储 |

#### 课程

| 泛雅字段 | 本系统字段 | 说明 |
|---|---|---|
| `courseId` | `TeachingCourse.ExternalID` | 课程外部 ID |
| `courseName` | `TeachingCourse.Title` | 课程名称 |
| `teacherInfo` | `TeachingCourse.TeacherID` / 教师用户 | 先同步教师，再绑定课程 |
| `schoolId` / `orgCode` | `TeachingCourse.OrgCode` | 组织编码 |
| `schoolName` | `TeachingCourse.SchoolName` | 学校名称 |
| `semester` / `term` | `TeachingCourse.Semester` | 学期 |
| `credit` | `TeachingCourse.Credit` | 学分 |
| `period` | `TeachingCourse.Period` | 学时 |
| `courseCover` | `TeachingCourse.CoverURL` | 封面 |

#### 班级/选课

| 泛雅字段 | 本系统字段 | 说明 |
|---|---|---|
| `classId` | `CourseClass.ExternalID` | 班级外部 ID |
| `className` | `CourseClass.ClassName` | 班级名称 |
| `classCode` | `CourseClass.ClassCode` | 班级编码 |
| `role` | `CourseEnrollment.Role` | teacher / student |
| `status` | `CourseEnrollment.Status` | active 等 |

### 7.2 不建议的做法

- 不要把“权限”只当成前端显示开关，必须落到 `role/status/enrollment`。
- 不要只同步用户不同步课程和班级，否则学生端无法形成可学习范围。
- 不要使用不稳定的外部 ID，否则重复同步会生成脏数据。

## 8. 联调验收口径

建议按下面顺序验收：

1. 先同步教师用户。
2. 再同步课程，确认课程负责人被正确绑定。
3. 再同步学生用户，确认 `PlatformUser` 能落库。
4. 再同步学生选课关系，确认学生可见课程。
5. 最后检查平台总览、用户列表、课程列表、班级列表、选课列表是否能正确过滤。

验收时重点关注：

- `PlatformUser.ExternalID` 是否唯一。
- `CourseEnrollment` 是否出现重复绑定。
- `OrgCode` 是否能正确分租户/分学校聚合。
- `role` 是否在教师/学生场景下正确落库。

## 9. 常见问题

### 9.1 为什么用户同步只传 userId 就能成功？

因为当前实现对 `syncUser` 的硬必填只有 `userInfo.userId`。其他字段会补齐到平台用户档案中，但不作为阻断条件。

### 9.2 为什么联系方式字段要加宽？

因为当前联系方式会先加密再落库，密文长度可能明显大于原始手机号/邮箱长度；如果列宽过小，会触发数据库写入错误。

### 9.3 为什么默认只签名 platformId 和 userId？

因为开放接口签名当前按“顶层平铺字段”做，默认只校验 `platformId,userId`，这样可以降低复杂 JSON 序列化差异带来的签名偏差。

### 9.4 选课关系为什么是权限核心？

因为课程可见性、学习范围、教师授课范围，最终都要通过 `CourseEnrollment` 和课程/班级归属来判定；它是比“单纯角色字段”更可靠的权限边界。
