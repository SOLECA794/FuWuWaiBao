# 课件解析核心链路：设计原理与需求对照

> 本文件梳理项目核心功能的链路设计原理，对照需求文档的系统性、完整性，帮助理解"每个环节为什么这么设计"以及"设计是否足够闭环"。

---

## 一、系统顶层设计：五环节闭环

### 1.1 核心链路全景

```
泛雅平台课件（PPT/PDF）
        │
        ▼
    ┌──────────────┐
    │  ① 课件解析   │  ← 文本提取 + 多模态视觉描述
    │  内容重构     │  ← 语义节点聚合 (跨页)
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  ② 智能讲授   │  ← 结构化脚本 (segment级)
    │  语音合成     │  ← TTS / 音频生成
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  ③ 实时问答   │  ← 上下文关联 + 多轮交互
    │  打断响应     │  ← SSE 流式输出
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  ④ 进度续接   │  ← NLP 三态理解 → resume_node_id
    │  节奏调整     │  ← 按理解程度调整
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  ⑤ 闭环反馈   │  ← 学习数据 → 泛雅回传
    └──────────────┘
```

**设计原则**：每一环节的输出是下一环节的输入，任一环节缺失都会导致体验断裂。

## 二、环节一：课件解析与内容重构

### 2.1 链路设计

```
PPT/PDF (上传)
    │
    ▼
┌─────────────┐
│ 文本提取     │  ← PyMuPDF (PDF) / python-pptx (PPT)
│ 多模态视觉   │  ← glm-4v-flash 描述公式/图表/流程图
│ (开关控制)   │  ← AI_USE_VISION=true/false
└──────┬──────┘
       ▼
┌─────────────┐
│ 内容重构     │  ← Stage 1: 课件理解
│             │  ← Stage 2: 语义节点聚合 (跨页)
│             │  ← Stage 3: 节点级脚本生成
└──────┬──────┘
       ▼
┌─────────────┐
│ 结构化输出   │  ← node_tree + scripts + segments
│ 增强 schema  │  ← segment_type/interaction_hint/etc.
└─────────────┘
```

### 2.2 关键设计决策

**为什么不用纯文本来提取得知识图谱？**
- 实测 12MB 计算机网络 PPTX（138 页）：纯文本提取 0 非空页
- 138 页中有 116 页包含图片/图表/流程图——纯文本模式下公式、拓扑图、表格全部丢失
- 结论：纯文本提取在真实课件中严重不足，多模态视觉描述是必需的

**多模态解析的两个路径：**
- PPTX：直接从 zip 包提取嵌入图片（`_extract_pptx_images`）→ base64 → glm-4v-flash
- PDF：`page.get_pixmap(dpi=150)` → PNG → base64 → glm-4v-flash
- 两者都不需要 LibreOffice 或 pdfplumber 等外部依赖

**为什么选择三阶段 pipeline 而非一次性生成？**
- 一次性生成时，LLM 容易"遗忘"前面的页面内容，跨 3-5 页的知识点聚合质量差
- Stage 1（课件理解）建立整体认知；Stage 2（语义聚类）跨页聚合节点；Stage 3（脚本生成）聚焦单节点生成详细讲稿
- 解耦后每一阶段可独立替换模型或优化 prompt

### 2.3 性能实测

| 指标 | 实测值 | 需求要求 | 达标 |
|------|-------|---------|------|
| 解析耗时（62KB PPTX） | 6.8s | ≤120s | ✅ 快 17 倍 |
| 问答延迟 | 5.0s | ≤5s | ✅ 达标 |
| API 接口数 | 15 个 | ≥10 个 | ✅ |

## 三、环节二：智能讲授（结构化脚本）

### 3.1 脚本结构设计

传统方案：整页拼接 → 输出一大段讲稿文本

本项目增强方案（`build_enhanced_script_schema`）：

```json
{
  "scripts": [{
    "node_id": "node_001",
    "title": "转发与路由的区别",
    "segments": [{
      "segment_id": "seg_001",
      "segment_type": "opening",
      "text": "我们先来看转发和路由的核心区别...",
      "estimated_seconds": 30,
      "difficulty": 0.3,
      "interaction_hint": "提问：你们觉得转发和路由哪个更重要？",
      "knowledge_card": {
        "type": "definition", "term": "转发",
        "definition": "将数据报从输入端口交换到输出端口的过程",
        "tags": ["网络层", "核心概念"]
      }
    }]
  }],
  "node_tree": {
    "nodes": [{
      "node_id": "node_001",
      "title": "转发与路由的区别",
      "summary": "区分数据平面转发和控制平面路由",
      "source_span": "第1-3页",
      "prerequisites": []
    }]
  }
}
```

**为什么用 segment_type 这种颗粒度？**
- 传统讲稿是一整段文本，学生打断后只能从头续接
- segment 级粒度允许按理解程度精确续接：partial 时跳到对应 segment
- interaction_hint 为教师提供互动话术，不只是一个单向播报的脚本
- knowledge_card 为后续问答提供上下文锚点

### 3.2 与需求对照

需求要求：
- ✅ "识别课件知识点、公式图表等" → 多模态解析 + 语义节点聚合
- ✅ "生成含开场白、讲解、过渡语的结构化脚本" → segment_type 体系覆盖
- ✅ "对接语音合成 API" → `/generate-audio` 路由，支持多音色
- ✅ "提供教师脚本编辑功能" → 教师端脚本面板可编辑

## 四、环节三：实时问答交互

### 4.1 上下文关联模型

```
学生提问 (文字/语音)
       │
       ▼
┌──────────────────┐
│ 上下文拼接        │  ← page_context + node_context + history
│ ask-with-context  │  ← AI_USE_VISION 开关
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 苏格拉底式回答    │  ← 不直接给答案，分步引导
│ SSE 流式输出      │  ← 打字机效果，低延迟感
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 对话持久化        │  ← session / dialogue_turns / question_logs
│ 多轮交互         │  ← history_summary + recent_turns 传递
└──────────────────┘
```

**为什么用 SSE 而非 HTTP？**
- 典型 AI 问答耗时 3-5 秒，HTTP 响应要等全部生成完毕才返回
- SSE 让第一个 token 在 0.5 秒内到达，感知延迟大幅降低
- 前端打字机效果叠加，用户几乎感受不到等待

**上下文关联的三层策略：**
1. `pageContextText`：当前页全文 → 最基础的上下文
2. `buildNodeScopedContext`：当前节点的片段 → 精确到知识点
3. `buildPageContextFromTeachingNodes`：当以上都为空时 → 从节点表构建

### 4.2 与需求对照

需求要求：
- ✅ "文字/语音打断提问" → 文字输入框 + SSE 输出
- ✅ "AI 结合上下文精准解答" → 三层上下文拼接策略
- ✅ "支持多轮交互" → session + history_summary + recent_turns
- ⚠️ "语音问答入口" → `/generate-audio` 路由存在，前端 TTS 集成依赖浏览器

## 五、环节四：进度续接与节奏调整

### 5.1 三态理解引擎

```
学生提问
    │
    ▼
┌────────────────────┐
│ _predict_understanding  │
│ LLM 分析问题+内容+历史  │
│ → none / partial / full │
└────────┬───────────┘
         ▼
    ┌────┴────┐
    │         │
   none    partial
    │         │
    ▼         ▼
resume=    resume=
page=同页    page=同页
sec=0       sec=偏移15s
    │         │
    └────┬────┘
         │
        full
         │
         ▼
    resume=
    page=下一页
    node=下一节点
```

**为什么用 LLM 做理解度分析而不是规则关键词？**
- 关键词匹配（"听不懂"→none、"继续"→full）精度低，实际对话千变万化
- LLM 可结合问题语义 + 课件内容 + 对话历史综合判断
- 实测 20 条测试：none 准确率 100%，partial 87.5%，full 80%，整体 90%

**节点级续接 vs 页级续接对比：**

| 场景 | 页级续接 | 节点级续接 | 节省 |
|------|---------|-----------|------|
| 部分理解 | 从头讲整页 | 跳到对应节点 + 偏移 | ~15s |
| 完全理解 | 讲完本页再翻页 | 直接跳下一页 | ~60s |
| 未理解 | 从头讲整页 | 从头讲整页 | 相同 |

### 5.2 数据流（本次修复完成）

```
AI 引擎返回 AskWithContextResponse
  ├── resume_page, resume_node_id, resume_sec     ← 三态值
  └── intent.understanding_level                   ← "none|partial|full"

Go 后端 SSE final 事件透传至前端
  ├── understanding_level
  └── resume_page / resume_node_id / resume_sec

前端 StudentAskPanel 展示
  ├── 理解度徽章 (level-none/partial/full)
  └── 续接 badge: "续接 2页 15s"
```

### 5.3 与需求对照

- ✅ "通过 NLP 分析学生理解程度" → `_predict_understanding()` 三态
- ✅ "自动定位原节点" → `_resolve_resume_strategy()` + resume_node_id
- ✅ "补充未理解内容" → none→从头, partial→偏移
- ✅ "提供进度可视化" → 学生端学习状态面板

## 七、设计可解释性总结

**一句话讲清楚项目做了什么：**
将 PPT/PDF 课件通过 AI 解析为结构化知识点，生成带互动话术的讲授脚本，学生可以在线打断提问，AI 根据理解程度自动决定从哪里继续讲。

**四个核心技术选型背后的理由：**

| 选型 | 理由 |
|------|------|
| glm-4v-flash 做视觉描述 | 配额可用 0.01 元/次，支持 base64，免部署 |
| 三阶段 pipeline | 跨页语义聚合需要独立认知阶段，一次生成会遗忘前文 |
| segment 级脚本 | 精确续接必需，无此粒度无法定位到具体时间点 |
| SSE 流式输出 | 5 秒绝对延迟不可接受，SSE 让首 token 0.5 秒到达 |

**一句话说清节点级续接优于页级：**
页级续接是"重听整页录音"，节点级续接是"跳到对应知识点继续讲"——前者浪费学生时间，后者尊重学生的理解进度。
